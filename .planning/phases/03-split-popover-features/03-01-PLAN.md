**types.ts — add conditionResults to StepResult (per D-02):**

Add an optional `conditionResults` field to `StepResult`:
```typescript
conditionResults?: { name: string; value: unknown; passed: boolean }[];
```
This field is present only on split steps. Each entry corresponds to one top-level condition in the filter group, with the resolved payload value and whether that condition passed.

**executionEngine.ts — new evaluateFilterGroupWithResults function (per D-03):**

Create a new function `evaluateFilterGroupWithResults` that mirrors `evaluateFilterGroup` but returns both the boolean AND the per-condition results array. Do NOT modify the existing `evaluateFilterGroup` signature — keep it for backward compatibility. The new function:

1. Maps each condition to `{ name, value, passed }` where:
   - `name` = the filter's `name` field (e.g., "contact.tier")
   - `value` = the resolved payload value via `getNestedValue` (the ACTUAL value, not the filter's comparison value)
   - `passed` = the boolean result of evaluating that condition
2. For nested FilterGroup conditions, recursively call `evaluateFilterGroupWithResults` and flatten results.
3. Returns `{ passed: boolean, conditionResults: { name: string; value: unknown; passed: boolean }[] }`.

Modify `evaluateStep` for the `split` case to call `evaluateFilterGroupWithResults` and include `conditionResults` in the returned `StepResult`.

**Do NOT change:**
- The `evaluateFilter` function — it stays as-is
- The `evaluateFilterGroup` function — it stays as-is (backward compat)
- Any other step kind evaluation logic

**Modify executeTrace to implement stop-on-failure (per D-12, D-13, D-14, D-15):**

In the `executeTrace` BFS loop, after evaluating each step and pushing its result:

1. **Stop on failure (D-12):** If `result.passed === false`, `break` the while loop. Do NOT enqueue children.
2. **Split 'no' is valid (D-14):** `branchTaken === 'no'` does NOT count as a failure. The split step's `passed` is always `true` — only a runtime error makes it fail. Check: if `result.passed === false && result.kind === 'split'`, that means a runtime error occurred (D-15) — stop the flow.
3. **Unexecuted steps (D-13):** Steps after the failed step are never evaluated, so they never appear in `results`. This is already handled by the break — no additional logic needed.
4. **Error on split failure (D-15):** In `evaluateStep` for the split case, if `evaluateFilterGroupWithResults` throws or a filter references a missing path, set `passed: false` with an appropriate error message. Wrap the filter evaluation in try-catch for robustness.

The BFS queue prepend behavior (children before remaining main path) stays unchanged.

**Do NOT modify:** trigger evaluation (always first, always pushed). The trigger step is evaluated before the loop — it is never subject to stop-on-failure since it has no prior step to fail.
  </action>
